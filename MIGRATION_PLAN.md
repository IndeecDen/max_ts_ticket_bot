**Зафиксированное требование пользователя:** Telegram и MAX — два самостоятельных бота. Каждый работает независимо: отдельный проект, процесс, токен, база данных, пользователи, роли, заявки, нумерация, статистика, настройки, очереди, журналы и резервные копии. MAX использует функциональность Telegram-бота как образец, но не зависит от его файлов или работающего процесса. Синхронизация и перенос данных между ботами не предусматриваются.

Перенос основного сценария технически возможен: сбор обращений, ожидание ответа специалиста, создание заявки в рабочем чате, назначение, закрытие, отмена, роли, отчёты, вложения, объявления и расписания. Сохранить можно бизнес-функции; интерфейс меню и навигацию к исходным сообщениям потребуется адаптировать.

Предлагается сохранить Python, SQLite, расчёты статистики и проверенные правила жизненного цикла заявки. Обработчики aiogram заменить независимыми обработчиками событий MAX. Для первой версии — асинхронный REST-клиент поверх aiohttp и HTTPS-сервер Webhook; SQLite и openpyxl достаточно для текущего масштаба. Это проектное решение, а не требование MAX. Документация предлагает примеры библиотек JavaScript и Go, но HTTP API не привязан к языку. [Разработка и примеры](https://dev.max.ru/help/chatbots)

## Условия осуществимости

1. На платформе MAX нужен верифицированный профиль организации, ИП или самозанятого — резидента РФ. Созданный бот проходит модерацию, после которой доступен токен. Наличие подходящего профиля проверяется до разработки интеграции. [Создание бота](https://dev.max.ru/docs/chatbots/bots-create/create)
2. Добавление бота в группы нужно разрешить в его настройках; исходно оно запрещено. [FAQ](https://dev.max.ru/help/chatbots)
3. Для получения событий клиентских групп и рабочего чата бот должен быть их администратором. Если клиент не может выдать эти права, полный групповой сценарий не обещаем: предлагаем приём обращений через личный диалог с ботом. [Получение событий](https://dev.max.ru/docs-api/methods/GET/updates)
4. Для рабочего запуска нужен HTTPS Webhook с доверенным сертификатом; Long Polling оставляем только разработке и тестированию. Endpoint должен отвечать HTTP 200 в пределах 30 секунд. Используем секрет подписки и проверяем заголовок `X-Max-Bot-Api-Secret`. [Webhook](https://dev.max.ru/docs-api/methods/POST/subscriptions)

Локальная папка проекта не заменяет постоянно работающий сервер. Для production понадобятся сервер, домен и HTTPS; для локальных живых испытаний — тестовый HTTPS-адрес либо поддерживаемый режим опроса.

## Ограничения, которые должны попасть в проектирование

- У MAX строковый идентификатор сообщения `mid`. Поля исходного сообщения и карточек в новой БД должны быть `TEXT`, а не Telegram-ориентированные целые числа. [Получение сообщения](https://dev.max.ru/docs-api/methods/GET/messages/-messageId-)
- Текст ограничен 4000 символами. Отправка ограничена двумя сообщениями в секунду на получателя. [Отправка](https://dev.max.ru/docs-api/methods/POST/messages)
- В личном диалоге сообщение без кнопок редактируется в пределах семи суток; сообщение с inline-кнопками — независимо от возраста. В группах ограничение по возрасту не указано. Редактирование также ограничено двумя операциями в секунду на чат. Для активной личной карточки оставляем кнопку «Статус», а при невозможности редактирования отправляем новую карточку и обновляем её ID. [Редактирование](https://dev.max.ru/docs-api/methods/PUT/messages)
- Удаление требует соответствующих прав и ограничено двумя операциями в секунду на чат; в личной переписке бот удаляет свои сообщения. [Удаление](https://dev.max.ru/docs-api/methods/DELETE/messages)
- Ответы на callback имеют собственное ограничение скорости. Подтверждение действия не должно ждать генерации отчёта или загрузки файла. [Callback](https://dev.max.ru/docs-api/methods/POST/answers)
- Медиа загружаются отдельно; сохраняем токены результата загрузки. Ошибка `attachment.not.ready` означает необходимость отложенной попытки. Обычный файл отправляется отдельным сообщением, к нему можно добавить клавиатуру; не объединяем его с фото/видео в одном сообщении. [Медиа](https://dev.max.ru/docs-api/use-cases/sending-messages/media)
- По текущему обзору API используется `platform-api2.max.ru`, авторизация в заголовке; общий ориентир — до 30 запросов/сек. Указаны требования доверия к сертификату Минцифры: проверяем TLS именно из окружения запуска и настраиваем доверенные CA, не отключаем проверку TLS. `GET /chats` больше не является способом перечисления чатов: ведём реестр по событиям. [Обзор API](https://dev.max.ru/docs-api)
- У ряда методов HTTP 200 может содержать `success=false`. Клиент проверяет и HTTP-статус, и результат в JSON. [Редактирование](https://dev.max.ru/docs-api/methods/PUT/messages)

Общий ограничитель запросов и ограничения отдельных операций на чат делаем настраиваемыми. Для первого запуска выбираем консервативный общий предел операций на получателя; после испытаний уточняем независимость квот.

## Поэтапная реализация

### Этап 0. Проверка доступа и короткий прототип API

Действия:

- Проверить регистрацию/модерацию, получить токен локально через `.env`.
- Подготовить рабочую группу, клиентскую группу и личный диалог тестового пользователя.
- Разрешить добавление бота в группы, выдать необходимые права.
- Проверить получение обычных сообщений без упоминания бота, сообщений специалиста, фото/видео/документа и callback.
- Отправить карточку с кнопкой, изменить её, удалить; проверить загрузку небольшого XLSX.
- Проверить TLS и Webhook; получить ID чатов из событий.
- Сохранить обезличенные образцы JSON для контрактных тестов.

**Результат:** протокол возможностей на реальном аккаунте. **Условие перехода:** получено событие из клиентской группы и выполнено действие кнопки в рабочей. Если групповые права недоступны — отдельно зафиксировать сокращённый вариант с приёмом заявок в личном диалоге. На этом этапе снимается главный риск переноса.

### Этап 1. Основа отдельного MAX-проекта

- Подготовить структуру, зависимости, `.env.example`, `.gitignore` и запуск.
- Ввести собственные модели пользователя, адресата, сообщения, вложения и нажатия кнопки — без типов aiogram.
- Реализовать REST-клиент: сообщения, обновление, удаление, callback, загрузка, сведения о чате и администраторах.
- Добавить обработку HTTP/JSON ошибок, таймаутов, ограничений скорости и журнал без токенов.
- Предусмотреть `MAX_API_BASE_URL`, `MAX_BOT_TOKEN`, `WORK_CHAT_ID`, `WEBHOOK_URL`, `WEBHOOK_SECRET`, `DATABASE_PATH`, `TIMEZONE` и путь доверенных CA при необходимости.

**Результат:** приложение получает событие и отправляет ответ через тестируемый адаптер. **Проверка:** контрактные тесты API проходят без сети; живой smoke-тест проходит с токеном.

### Этап 2. Надёжные входящие события, данные и таймеры

- Спроектировать новую БД, не использовать рабочий Telegram `bot.db` как базу MAX.
- Перенести `requests`, ожидающие обращения, медиа и очередь доставки с адаптацией типов ID.
- Добавить `inbox_events`, реестр чатов, состояния диалогов, учёт выполнения расписаний.
- Webhook: проверить секрет → сохранить событие транзакцией → вернуть HTTP 200 → обработать фоновым worker.
- Дедупликация новых сообщений по типу события и `mid`, нажатий — по `callback_id`. Для редактирований и других событий выбрать ключ по реальным схемам; не предполагать наличие универсального `update_id`.
- Для тестового Long Polling сохранять `marker` только после надёжного сохранения полученной пачки.
- Хранить временные метки единообразно; расписание рассчитывать в явно заданном часовом поясе.

**Результат:** принятые обращения переживают остановку процесса. **Проверка:** повтор события не создаёт вторую заявку; сбой между сохранением и обработкой безопасен; задержанная доставка не теряется.

### Этап 3. Полный основной цикл заявки

- Перенести сбор текста/вложений, стоп-слова и ожидание ответа специалиста.
- Сохранить поведение нескольких клиентов в одном чате и отмену ожидания после ответа сотрудника.
- Реализовать `new → in_progress → closed` и отмену `new → canceled`.
- Проверять права, автора, ID исполнителя и допустимость перехода на каждом действии.
- Обновлять карточки клиента и рабочего чата через устойчивую очередь, с ревизиями статуса.
- Добавить повторные попытки, обработку недоступного чата и замену исчезнувшей карточки.

**Результат:** работоспособная первая версия — обращение проходит весь путь. **Проверка:** два специалиста одновременно нажимают «Взять» — назначается один; другой пользователь не закрывает чужую заявку; рестарт и сбой отправки не создают новую заявку.

### Этап 4. Меню, роли и настройки

- Перенести `/start`, `/help`, `/cancel`; добавить `/menu` и `/whoami` для получения собственного MAX ID.
- Сделать inline-меню клиента, специалиста и администратора; настройку прав по ID или выбором известного участника.
- Перенести управление специалистами и ботадминами, открытые/неназначенные/личные заявки, `/assign_request` и массовое закрытие.
- Перенести настройки таймаута, стоп-слов, объявлений и расписаний; сохранять шаги диалога в БД.
- Не строить назначение по `@username`: имя необязательно и не является идентификатором.
- Для «Обращение целиком» показывать сохранённые данные после проверки доступа; не конструировать недокументированные ссылки на сообщения групп.

**Результат:** ежедневные операции доступны через команды и меню. **Проверка:** таблица ролей покрыта тестами; старые кнопки после отзыва роли не предоставляют доступ; отмена диалога и возврат в меню работают.

### Этап 5. Вложения, отчёты и расписания

- Завершить загрузку/повторную отправку всех поддерживаемых исходным ботом медиа; обработать ещё не готовые вложения.
- Перенести общую/личную статистику: день, неделя, месяц, произвольный период.
- Перенести Excel, сохранение пользовательского ввода как текста и отправку файла через MAX.
- Добавить объявления с датой окончания и дневными/ночными интервалами.
- Перенести ежедневный дайджест, напоминания о неназначенных заявках и автоочистку.
- Учитывать лимиты при большой очереди, разбивать длинные отчёты, сохранять отметки выполненных расписаний.

**Результат:** достигнуто функциональное соответствие с оговорёнными изменениями интерфейса. **Проверка:** числа в отчётах совпадают с контрольными данными, XLSX открывается, после рестарта расписание не исполняется повторно без причины, неудачные удаления остаются на повтор.

### Этап 6. Испытания и пилот

- Адаптировать релевантные сценарии из текущих 30 регрессионных тестов; дополнить MAX-контрактами.
- Проверить дубли/перестановку событий, 429/5xx, медленную сеть, `success=false`, сбой обработки медиа, пропажу прав, удаление бота и прекращение личного диалога.
- Проверить повторный callback, одинаковые имена, смену имени, невалидные команды и длинный текст.
- Проверить пределы редактирования личных карточек через имитацию ответа API; отдельно подтвердить поведение на доступных реальных сообщениях.
- Провести пилот: один рабочий чат, один клиентский чат, несколько сотрудников, минимум полный цикл расписания.

**Результат:** протокол испытаний и список оставшихся ограничений. **Условие запуска:** нет потери уже сохранённых обращений, нарушения ролей и неконтролируемых повторов; восстановления и резервная копия проверены.

### Этап 6а. GitHub, README и автоустановка Debian/Ubuntu

Дополнение по требованию пользователя: проект распространяется через отдельный GitHub-репозиторий. README и установщик входят в обязательный объём первой версии, а не остаются задачами после запуска. Подготовить их до серверного пилота и проверить пилот через установщик.

1. **Подготовка репозитория.** Привести структуру к самостоятельному проекту MAX; исключить из Git токены, `.env`, базы, резервные копии, журналы, виртуальное окружение и временные отчёты. Добавить GitHub Actions для автономных тестов и проверок установочных файлов. Документировать выпуск версий; фактический URL репозитория использовать после его создания, не подставлять выдуманный адрес.
2. **README для пользователя.** Переработать текущий журнал частей в цельное руководство: возможности и ограничения MAX, поддерживаемые версии Debian/Ubuntu и Python, требования к серверу и правам бота, создание бота и получение ID, подготовка DNS/HTTPS, установка из GitHub, настройки, команды и роли, запуск/остановка, обновление, журналы, диагностика, резервное копирование, восстановление и удаление службы. Историю разработки оставить в плане или отдельном документе. Примеры должны запускаться на чистом сервере без Windows-путей и Telegram-проекта.
3. **Интерактивный установщик `scripts/install.sh`.** Проверить ОС, наличие systemd и необходимые права; установить системные зависимости, получить выбранную версию проекта, создать отдельного системного пользователя, каталоги, Python venv и зависимости из закреплённого списка. До изменения существующей установки показать режим: новая установка или обновление. Повторный запуск не должен создавать вторую службу, стирать базу или сбрасывать роли.
4. **Пошаговый ввод настроек.** Запросить MAX-токен без отображения, рабочий и клиентские чаты, начальных администраторов/специалистов, часовой пояс, таймауты, параметры локального HTTP-сервера и публичный адрес Webhook. Предложить генерацию секрета Webhook. Проверять значения до сохранения; сохранять всё необходимое для повторного запуска службы, включая параметры, которые сейчас передаются флагами CLI. Ограничить доступ к секретам и не помещать токены в командную строку или журналы. При обновлении сохранять текущие значения; первоначальные роли не должны перезаписывать уже изменённые роли из базы.
5. **HTTPS и подписка MAX.** Предусмотреть режим собственного reverse proxy и режим уже существующего HTTPS-прокси. Дать все шаги DNS, сертификата, маршрута Webhook и сетевого доступа; не менять чужие сайты. Проверить доступность endpoint и затем регистрировать подписку с тем же секретом, без дублей при повторном запуске. Если DNS/сертификат/доступ MAX ещё не готовы, сообщить точный незавершённый шаг и способ продолжить установку.
6. **Автоматическая служба systemd.** Создать unit `max-ts-ticket-bot.service` с отдельным пользователем, корректными рабочим каталогом, окружением, командой запуска venv, автоперезапуском и корректной остановкой. Выполнить `daemon-reload`, включить автозапуск и запустить службу после проверки конфигурации. Проверить состояние systemd и `/readyz`; вывести команды просмотра статуса, журналов, остановки и перезапуска. Файлы службы и данные MAX не должны затрагивать Telegram-бота.
7. **Обновление и обслуживание.** Предусмотреть резервную копию SQLite перед миграциями с учётом WAL, обновление кода/зависимостей и перезапуск с проверкой готовности. Документировать согласованный откат кода и базы. Удаление службы по умолчанию сохраняет настройки и данные; окончательное удаление данных — отдельное явное действие оператора.
8. **Проверка установки.** Выбрать и явно зафиксировать поддерживаемые выпуски ОС после проверки совместимости. Испытать на чистых Debian и Ubuntu с настоящим systemd: установка с нуля, повторная установка, обновление, некорректные настройки, сбой сети/зависимостей, восстановление из резервной копии и автозапуск после перезагрузки. Shell-проверки и имитации дополняют, но не заменяют серверные испытания.

**Планируемые файлы:** `README.md`, `scripts/install.sh`, `deploy/max-ts-ticket-bot.service`, примеры конфигурации, документация по обновлению/восстановлению и workflow GitHub Actions. Дополнительные скрипты создавать по необходимости.

**Критерий готовности:** пользователь следует README на чистом поддерживаемом Debian/Ubuntu, запускает установщик, вводит настройки и получает установленную службу MAX с автозапуском, проверенной готовностью и понятной диагностикой. Для полностью рабочего Webhook должны быть выполнены явно указанные внешние условия DNS, HTTPS и доступа MAX. Этап выполняется: первичная версия установщика и unit реализована в части 20; оставшиеся пункты и Linux-пилот ещё не завершены.

### Этап 7. Независимый запуск MAX-бота

- Развернуть HTTPS endpoint, зарегистрировать подписку и проверить сертификаты/секрет.
- Настроить автозапуск, резервное копирование SQLite, контроль ошибок и длины очереди.
- Начать с одного экземпляра приложения; масштабирование и PostgreSQL вводить по фактической нагрузке.
- Подключать клиентские группы постепенно, выдавать сотрудникам роли MAX отдельно.
- Подготовить инструкции и процедуру отката только MAX-проекта.

**Результат:** самостоятельный MAX-бот с наблюдаемой доставкой. Telegram-бот продолжает работать независимо; запуск, остановка, обновление или сбой MAX-бота не должны влиять на него.

## Разделение проектов и данных

MAX начинает работу с собственной новой базой. История Telegram остаётся исключительно в Telegram-проекте. Импорт истории, сопоставление аккаунтов и объединённая статистика не входят в этот проект.

Настройки и роли MAX задаются заново. Заявки и номера формируются независимо, даже если обоими ботами пользуются одни и те же сотрудники. Общих очередей, таблиц, токенов и состояния диалогов нет. При разработке можно адаптировать алгоритмы и тестовые сценарии, но MAX-проект должен запускаться и тестироваться без установленного Telegram-проекта. Никакого прекращения приёма заявок в Telegram в плане нет.

## Порядок и границы первой версии

Порядок: **проверка API → основа → сохранность → цикл заявки → управление → отчёты и расписания → GitHub, README и установщик → серверные испытания и пилот → запуск**.

Отдельный веб-интерфейс и мини-приложение MAX в первую версию не входят. Объединение двух ботов, общий процесс, общая база, синхронизация и перенос истории исключены из проекта согласно требованию независимой работы.

Проверенные документы подтверждают доступность API, но не права конкретного аккаунта, допустимость конкретного XLSX и поведение всех клиентов MAX. Поэтому этап 0 обязателен до обещания полного соответствия. Оценку трудозатрат уточняем после него; срок модерации и подготовка HTTPS — внешние зависимости.

Для начала живых испытаний понадобятся: созданный бот и локально сохранённый токен, тестовые группы с правами, пользователи для проверки ролей и доступный HTTPS endpoint. Для проверки доступа к API уже подготовлена команда `python -m app.main check-api`; полный сценарий бота ещё разрабатывается.
