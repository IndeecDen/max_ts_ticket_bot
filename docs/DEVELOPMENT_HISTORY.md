# MAX-бот техподдержки

Самостоятельный проект: собственные настройки, окружение и база MAX. Импорта кода, базы и токена Telegram-бота нет.

Первая версия установки Debian/Ubuntu: [руководство](LINUX_INSTALL.md). Linux/systemd ещё требуют живых испытаний.

## Часть 1 — основа и проверка подключения

Готово:

- загрузка `.env` из папки проекта и проверка конфигурации;
- отдельный API-клиент: сведения о боте, чате и правах бота;
- обработка HTTP/JSON ошибок, ограничения частоты и таймаутов;
- обязательная проверка TLS, поддержка дополнительного CA-файла;
- безопасные сообщения об ошибках без токена и сырого ответа сервера;
- автономные тесты с имитацией HTTP-ответов.

## Часть 2 — сохранение входящих событий

Реализованы отдельная SQLite-база и Webhook-приёмник. Режим `collect_only`: события сохраняются, но заявки и ответы пользователям пока не создаются. Живые проверки этапа 0 ещё предстоят.

- секрет проверяется до обращения к базе;
- HTTP 200 отправляется после фиксации события в SQLite; при ошибке записи возвращается 503;
- сообщения дедуплицируются по `mid`, нажатия — по `callback_id`, остальные события — по полному содержимому;
- неизвестные типы событий сохраняются целиком, различные редакции сообщений не объединяются;
- сохранённые события переживают перезапуск; чужая база не принимается для миграции;
- SQLite работает вне цикла обработки сетевых запросов.

Команда `serve` только сохраняет события. Отдельный локальный обработчик описан ниже. Базовое меню описано в части 17; текстовые отчёты описаны в части 10; автоматическое удаление и срок хранения пока не настроены.

## Часть 3 — локальная обработка и начало заявки

Команда `process-inbox` обрабатывает до 100 сохранённых `message_created` за запуск и не обращается к сети. В `.env` должен быть задан `WORK_CHAT_ID`. Передайте полный список клиентских чатов и MAX ID специалистов (включая сотрудников, чьи ответы должны отменять ожидание). ID из примера замените своими:

```powershell
.\.venv\Scripts\python.exe -m app.main process-inbox --client-chat=-20 --specialist=99 --timeout=300
```

Для нескольких чатов или сотрудников повторяйте соответствующий параметр. Рабочий чат исключён из клиентских. Список клиентских чатов задаётся при каждом запуске. Начиная с части 8, роли сохраняются в базе: `--specialist` и `--bot-admin` используются только при первоначальном заполнении. Проверка администраторов самого MAX через API ещё не подключена.

- Сообщения одного пользователя в одном чате собираются в обращение `waiting`; другие пользователи ожидают независимо.
- Время ожидания отсчитывается от локального получения первого сообщения. Дополнительные сообщения не продлевают его.
- Ответ указанного специалиста отменяет все `waiting` в этом чате. После истечения ожидания обращение становится `new` при следующем запуске команды.
- Перед переводом в `new` обработчик разбирает накопленные сообщения, в том числе ответ специалиста в следующем пакете. Если команда сообщает об остатке, повторите её.
- Если уже есть `new`, повторная заявка того же клиента в том же чате не создаётся. Новые сообщения остаются в inbox с результатом `active_request_exists`.
- Изменение обращения и отметка обработки события фиксируются одной транзакцией. При сбое пакет откатывается; повторный запуск безопасен. Схема базы обновляется с версии 1 до 2 с сохранением inbox.

Боты, отправители без явного `is_bot: false`, пустые сообщения, команды и сообщения вне разрешённых чатов не создают обращений; причина записывается в `inbox_events.outcome`, оригинал остаётся в базе. Такие события автоматически повторно не обрабатываются при смене параметров. Callback обрабатываются по правилам части 6; редактирования и неизвестные типы пока остаются необработанными. Исходные JSON с вложениями и пересылками сохраняются, но файлы пока не скачиваются и не отправляются. Структура сообщения сверена с [объектом Message MAX](https://dev.max.ru/docs-api/objects/Message).

Команда `process-inbox` только создаёт задания доставки, не отправляя карточки. Стоп-слова реализованы в части 9; личные диалоги без `chat_id` ещё не поддерживаются. `serve` не запускает обработчик автоматически. Проверены 204 автономных теста.

## Часть 4 — очередь доставки карточек

При переводе обращения в `new` в той же транзакции создаются два задания: карточка в рабочий чат и уведомление в исходный клиентский чат. Для существующих заявок версии 2 задания создаются при следующем `process-inbox`. Текст и адресат фиксируются в очереди; повторная обработка их не дублирует. Схема базы — версия 3.

```powershell
# Только состояние очереди, без сети:
.\.venv\Scripts\python.exe -m app.main queue-status

# Реальная отправка накопленных карточек (нужен MAX_BOT_TOKEN):
.\.venv\Scripts\python.exe -m app.main deliver-outbox
```

`deliver-outbox` выполняет до 100 доступных отправок и завершается. Если задания ожидают задержки, команду нужно повторить позже. Для фоновой отправки используйте режим `run`, описанный ниже; `serve` продолжает только принимать события. В ходе разработки реальные сообщения не отправлялись.

Карточки текстовые с кнопками управления заявкой (часть 6). Длинный текст сокращается до 3900 единиц UTF-16, полный оригинал остаётся в базе. Ссылки не получают предпросмотр, пользовательский текст отправляется без HTML/Markdown-разметки. Ограничение реализовано консервативно — не чаще одной отправки в секунду в чат, включая параллельные процессы и повторный запуск; [MAX допускает две отправки в секунду](https://dev.max.ru/docs-api/methods/POST/messages).

Состояния очереди:

| Состояние | Значение |
| --- | --- |
| `pending` | Ожидает отправки или повтора после HTTP 429; учитываются Retry-After и возрастающая задержка, максимум 10 попыток |
| `sent` | Успех подтверждён, строковый `mid` сохранён |
| `failed` | Постоянная ошибка, исчерпаны попытки или Retry-After превышает сутки; нужна проверка |
| `uncertain` | Таймаут, сбой сети, HTTP 5xx или некорректный успешный ответ: сообщение могло быть отправлено |
| `sending` | Отправка выполняется; после аварийной остановки также требует проверки |

`uncertain` и оставшиеся после аварии `sending` автоматически не повторяются: подтверждённой идемпотентности POST в используемом API нет. Проверьте наличие карточки в чате; команды ручной сверки и возобновления описаны в части 7. `sending` блокирует последующие отправки в тот же чат до разбирательства. При таких состояниях или `failed` команда доставки возвращает ненулевой код. Очередь не обеспечивает гарантированное «ровно один раз» между SQLite и внешним API.

## Часть 5 — фоновый режим

Команда `run` одновременно принимает Webhook, обрабатывает inbox, переводит истёкшие ожидания в заявки и отправляет карточки. Это режим с реальными отправками; требуются `MAX_BOT_TOKEN`, `WEBHOOK_SECRET`, `WORK_CHAT_ID` и параметры клиентских чатов и специалистов:

```powershell
.\.venv\Scripts\python.exe -m app.main run --client-chat=-20 --specialist=99 --timeout=300
```

Замените примерные ID своими. Запускайте один экземпляр `run` с неизменным полным списком чатов и специалистов; отдельные команды обработки и доставки при нём запускать не требуется. В обработку попадут и события, накопленные ранее через `serve`, а в отправку — существующие `pending`.

Обработка и доставка выполняются в независимых циклах с паузой в одну секунду. Ошибка одного цикла не останавливает другой и приём событий; ошибка журналируется без текста обращения и токена. Задержки и ограничение скорости из outbox сохраняются. `failed`, `uncertain` и прерванные `sending` не переотправляются автоматически.

Ctrl+C останавливает циклы с ожиданием текущей операции до `HTTP_TIMEOUT_SECONDS + 15` секунд, затем закрывает API-сессию. При превышении срока задача отменяется; неопределённое `sending` остаётся для проверки. После обычного перезапуска продолжаются сохранённые ожидания и допустимые отправки; подтверждённые `sent` повторно не отправляются.

В режиме `run` `/readyz` возвращает `mode: bot`, состояние циклов и количества заданий по состояниям. До первого успешного прохода, при ошибке цикла, `failed`, `uncertain` или обнаруженной прерванной отправке возвращается HTTP 503. `/healthz` отдельно подтверждает доступность HTTP-процесса. После ручного разбора отправок, прерванных до запуска, требуется перезапуск для сброса стартового предупреждения. Это диагностика локального процесса, а не подтверждение прав в MAX или доступности публичного HTTPS.

Полный путь Webhook → SQLite → ожидание → две карточки проверен локально с имитацией MAX. Проверены остановка во время отправки, принудительная отмена, восстановление после ошибки базы и повторный запуск. Живой пилот и регистрация подписки ещё впереди; базовый жизненный цикл реализован в части 6.

## Часть 6 — управление заявками

Рабочая карточка новой заявки содержит «Взять», а клиентская — «Отменить». После назначения в рабочей карточке появляется «Завершить». Закрытые и отменённые карточки остаются без кнопок.

| Действие | Кто и где может выполнить | Переход |
| --- | --- | --- |
| Взять | Пользователь с сохранённой ролью `specialist`, в рабочем чате | `new` → `in_progress` |
| Завершить | Назначенный исполнитель, по-прежнему входящий в список специалистов, в рабочем чате | `in_progress` → `closed` |
| Отменить | Автор заявки в её клиентском чате | `new` → `cancelled` |

Права администратора MAX сами по себе пока не дают дополнительных действий: используются роли из базы бота. Переназначение реализовано в части 8; административная отмена описана в части 19. Одновременные обращения одного клиента в одном чате запрещены также в состоянии `in_progress`; после закрытия или отмены можно создать новое.

Callback проверяется по MAX ID пользователя, чату, сохранённому `mid` карточки и номеру версии заявки. Повторная доставка одного callback не исполняет действие повторно. Нажатие устаревшей кнопки не меняет состояние. Причина отказа сохраняется в `inbox_events.outcome`; персональные пояснения в интерфейсе пока не добавлены.

Действие, отметка обработки и задания на обновление обеих карточек сохраняются одной транзакцией. Если новая версия появилась во время отправки старой, она остаётся в очереди. Подтверждённые карточки обновляются через [PUT /messages](https://dev.max.ru/docs-api/methods/PUT/messages), новые отправляются через POST; закрытие убирает клавиатуру явным `attachments: []`. Ответ на известный callback ставится в ту же очередь через [POST /answers](https://dev.max.ru/docs-api/methods/POST/answers), без замены карточки в самом ответе. Ограничение скорости общее для отправки, редактирования и ответа на кнопку.

Схема SQLite автоматически обновляется до версии 4 с сохранением заявок, исходных сообщений и ID карточек. После обновления `run` или `process-inbox` добавит кнопки существующим карточкам; `sent` с известным `mid` перейдут в очередь редактирования. Проблемные `failed`, `uncertain` и `sending` автоматически не сбрасываются. Перед обновлением остановите старый процесс и сохраните резервную копию базы.

Живые нажатия в MAX пока не проверены. Если сообщение удалено или MAX отклоняет редактирование, задание сохраняется как ошибка для разбора; автоматическая замена карточки ещё не реализована.

## Часть 7 — восстановление очереди

Все команды этого раздела работают только с локальной базой, без токена и сети. Наличие сообщения, его `mid` и фактическую версию проверяет оператор в MAX. При обновлении сначала остановите процессы старой версии: они ещё не используют блокировки восстановления. Текущая схема SQLite — 14.

```powershell
# До 100 проблемных заданий без текста обращений; подробности одного задания:
.\.venv\Scripts\python.exe -m app.main queue-inspect
.\.venv\Scripts\python.exe -m app.main queue-inspect --job-id=12

# Карточка найдена в MAX: привязать её mid и подтвердить фактическую версию:
.\.venv\Scripts\python.exe -m app.main queue-confirm --job-id=12 --revision=3 --delivered-revision=2 --message-id="mid-из-MAX" --reason="Проверена карточка в рабочем чате"

# Повтор после устранения постоянной ошибки или для известного mid:
.\.venv\Scripts\python.exe -m app.main queue-retry --job-id=12 --revision=3 --reason="Восстановлены права бота"

# Только если проверено, что отправки с неизвестным результатом не было:
.\.venv\Scripts\python.exe -m app.main queue-retry --job-id=12 --revision=3 --confirm-not-delivered --reason="Карточки в чате нет"
```

ID и версии в примерах замените значениями своего задания. `revision` — текущая версия из `queue-inspect`, `attempted_revision` — версия последней начатой попытки (для старых заданий может быть неизвестна). `delivered-revision` — версия фактически найденной карточки: если она ниже текущей, команда сохранит `mid` и поставит актуальный текст и кнопки на редактирование. При совпадении версий задание станет `sent`. Чужой или отличающийся от уже сохранённого `mid` не принимается.

`queue-retry` сбрасывает счётчик попыток и ошибку, сохраняя текущие текст, кнопки, адресата, версию и ограничения времени отправки. С известным `mid` выполняется редактирование; без него — новая отправка. Для `uncertain` или прерванного `sending` без `mid` требуется явное `--confirm-not-delivered`, поскольку ошибочное решение может создать дубль. Следующую операцию выполнит работающий `run` или отдельный `deliver-outbox`; сами команды восстановления ничего не отправляют.

Восстановление разрешено только для `failed`, `uncertain` и прерванного `sending`. Активная отправка защищена блокировкой ОС; после гибели процесса блокировка снимается, файлы блокировок остаются и удалять их во время работы нельзя. Блокировки находятся рядом с базой в `<имя-базы>.delivery-locks`; все экземпляры должны использовать один и тот же путь к базе на локальном диске.

Изменение состояния и запись в `recovery_log` происходят одной транзакцией. Журнал хранит действие, прежнее состояние, версии, `mid`, причину и время. Изменившаяся версия задания отклоняет устаревшую команду. Для подтверждения доставленного ответа на callback указывают `--delivered-revision=0` без `--message-id`.

После разбора прерванных отправок перезапустите `run`, чтобы сбросить стартовое предупреждение `/readyz`. Автоматического поиска сообщений в MAX, замены удалённых карточек и гарантии доставки «ровно один раз» по-прежнему нет.

## Часть 8 — роли и переназначение

Роли `specialist` и `admin` хранятся в отдельной базе MAX и проверяются внутри транзакции при обработке каждого действия. Это роли бота, они не выдаются автоматически администраторам чата MAX. Один пользователь может иметь обе роли. Только `specialist` позволяет брать и завершать заявки; `admin` даёт управление ролями и переназначение.

Первый запуск новой базы или первое включение обработки после обновления до схемы 6 импортирует указанные ID:

```powershell
.\.venv\Scripts\python.exe -m app.main run --client-chat=-20 --specialist=99 --bot-admin=77 --timeout=300
```

После первоначального заполнения эти параметры больше не меняют роли, даже при перезапуске. Их можно опустить, оставив `--client-chat`; изменение сохранённого таймаута описано в части 9. Чтобы добавить администратора в уже заполненную базу, используйте локальную команду:

```powershell
.\.venv\Scripts\python.exe -m app.main roles-list
.\.venv\Scripts\python.exe -m app.main role-grant --user-id=77 --role=admin
.\.venv\Scripts\python.exe -m app.main role-grant --user-id=99 --role=specialist
.\.venv\Scripts\python.exe -m app.main role-revoke --user-id=99 --role=specialist
```

Локальные команды доступны оператору с доступом к файлам проекта, не требуют токена и не обращаются к сети. Первое изменение роли локальной командой также фиксирует первоначальное заполнение: после него оставшиеся роли добавляйте командами, а не параметрами запуска. Пустая база без начальных ID не запускает обработчик. Удалить последнего администратора нельзя — сначала назначьте другого.

Администратор бота может отправлять в **рабочем чате**:

| Команда | Результат |
| --- | --- |
| `/roles` | Список ролей и MAX ID; длинный список сокращается, полный доступен через `roles-list` |
| `/role_grant specialist 101` | Выдать роль специалиста |
| `/role_revoke specialist 101` | Отозвать роль специалиста |
| `/role_grant admin 78` | Назначить администратора бота |
| `/role_revoke admin 78` | Отозвать роль администратора |
| `/reassign 12 101` | Переназначить заявку №12 специалисту 101 |

Команды обрабатываются в `run` либо отдельным `process-inbox`; ответы отправляются через outbox. Личные и клиентские чаты не принимают административные команды. Неавторизованные команды не изменяют данные; причина фиксируется в inbox. Повторная доставка одного сообщения не повторяет изменение или ответ.

Переназначать можно только `in_progress`, только действующему специалисту. Начальное время работы сохраняется, версия заявки увеличивается, обе карточки обновляются. Прежняя кнопка завершения становится устаревшей. Закрыть заявку может новый исполнитель. Отзыв роли действует на следующее обрабатываемое действие без перезапуска; уже назначенные заявки не закрываются автоматически — администратор должен переназначить их. Ответ администратора или специалиста в клиентском чате отменяет ожидания, как ответ сотрудника поддержки.

Изменения ролей и назначения записываются в `management_log` вместе с автором команды и ID события; у локального оператора `actor_id` пустой. Изменение, журнал, ответ и обновление карточек фиксируются одной транзакцией с обработкой события. Для работы этой части не требуется менять подписку Webhook. Живые административные команды в MAX пока не проверены.

## Часть 9 — время ожидания и слова-исключения

Настройки хранятся в SQLite, схема версии 7. При первом включении обработчика после обновления `--timeout` задаёт начальное время ожидания (по умолчанию 300 секунд). После этого перезапуск с другим `--timeout` не заменяет значение из базы. Изменения применяются при обработке новых событий без перезапуска.

Администратор бота может отправлять в рабочем чате:

| Команда | Действие |
| --- | --- |
| `/get_timeout` | Показать время ожидания |
| `/set_timeout 180` | Установить ожидание новых обращений, от 1 до 86400 секунд |
| `/list_ignore` | Показать слова-исключения |
| `/add_ignore спасибо ок понятно` | Добавить одно или несколько слов |
| `/del_ignore понятно` | Удалить слово |

Локальные команды оператора не требуют токена и сети:

```powershell
.\.venv\Scripts\python.exe -m app.main settings-show
.\.venv\Scripts\python.exe -m app.main timeout-set --seconds=180
.\.venv\Scripts\python.exe -m app.main ignore-add --word=спасибо --word=ок
.\.venv\Scripts\python.exe -m app.main ignore-remove --word=ок
```

До первоначальной настройки `settings-show` показывает `response_timeout: null`; при запуске обработчик сохранит `--timeout`. Явный `timeout-set` до запуска имеет приоритет. `settings-show` возвращает полный список исключений; ответ `/list_ignore` в MAX при необходимости сокращается.

Таймаут применяется только при создании нового ожидания. Уже сохранённый `due_at_ms` не пересчитывается; дополнительные сообщения клиента также не продлевают срок. События, ещё не обработанные из inbox, используют настройку на момент обработки. Изменение настройки, запись в журнал, отметка обработки команды и ответ через outbox фиксируются одной транзакцией.

Как в исходном Telegram-боте, сообщение игнорируется только если **все** его слова входят в список. Перед сравнением удаляются знаки ASCII-пунктуации (например, `!`, `,`, `.`), текст приводится к нижнему регистру и разбивается по пробелам. Подстроки не используются: исключение `ок` не отсекает `окно`. Unicode-знаки вроде `«»` отдельно не удаляются. При добавлении слова нормализуются тем же способом; пустые исключения и фразы одним аргументом не допускаются. До 100 слов за команду, до 64 символов в слове и до 1000 исключений в базе.

«Спасибо, но ошибка осталась» сохраняется как обращение. Отдельное «спасибо» не добавляется к уже ожидающему обращению, но не отменяет его. Вложения без текста сохраняются; вложение с подписью, целиком состоящей из исключений, игнорируется по правилу Telegram. Исходное событие остаётся в inbox с результатом `ignored_words` и автоматически повторно не обрабатывается после удаления исключения.

Ответ сотрудника обрабатывается до проверки слов-исключений и отменяет ожидания. Команда сотрудника в клиентском чате ожидания не отменяет. Все изменения настроек сохраняются в `management_log`. Живые команды в MAX ещё не проверены.

## Часть 10 — статистика завершённых заявок

В рабочем чате доступны команды:

| Команда | Доступ и период |
| --- | --- |
| `/stats` или `/stats day` | Администратор бота: общая сводка за сегодня |
| `/stats week` | Администратор: последние 7 календарных дней, включая сегодня |
| `/stats month` | Администратор: последние 30 календарных дней, включая сегодня |
| `/stats 2026-09-01 2026-09-22` | Администратор: обе даты включительно |
| `/my_stats week` | Специалист или администратор: только заявки, где он указан исполнителем |
| `/my_stats 2026-09-01 2026-09-22` | Личная сводка за произвольный период |

Ответ отправляется в тот же рабочий чат и виден его участникам; «личная» означает фильтр по исполнителю, а не приватную доставку. Чужой MAX ID в `/my_stats` задать нельзя. Доступ проверяется по текущим ролям из базы; клиентские чаты эти команды не исполняют.

Локальная сводка без сети и токена:

```powershell
.\.venv\Scripts\python.exe -m app.main stats --period=week
.\.venv\Scripts\python.exe -m app.main stats --from-date=2026-09-01 --to-date=2026-09-22
.\.venv\Scripts\python.exe -m app.main stats --period=month --user-id=99 --json-output
```

Локальный оператор может указать любого исполнителя. `--json-output` выводит структурированный результат в терминал; файл автоматически не создаётся. Локальная Excel-выгрузка описана в части 11.

В отчёт входят только `closed`, отобранные по `ended_at_ms`, как в Telegram по дате завершения. Незавершённые и отменённые обращения не учитываются. Границы — местная полночь в `TIMEZONE` (по умолчанию `Europe/Moscow`), начало включается, полночь следующего за последней датой дня исключается. Для команд относительный период определяется датой получения события ботом, для локального запуска — текущей датой. В MAX периоды week/month означают ровно 7/30 календарных дней, включая сегодня.

Сводка показывает количество закрытых заявок, среднее ожидание и выполнение, количество измерений и разбивку по парам «чат — исполнитель». Ожидание считается от получения первого сообщения до взятия заявки; оно включает первоначальный таймаут сбора. Выполнение — от первого взятия до завершения. После переназначения вся заявка относится к последнему исполнителю; распределение времени между сотрудниками пока не рассчитывается.

Отсутствующие или отрицательные интервалы не входят в соответствующее среднее. Среднее рассчитывается по всем допустимым измерениям, а не по средним групп. Продолжительность показана как часы:минуты:секунды, часы могут превышать 24. Длинная сводка разбивается на страницы без потери строк и отправляется через очередь с обычным ограничением скорости. Повторная доставка команды не создаёт второй отчёт.

Схема SQLite — 8: добавлен индекс для выборки по завершению, данные сохранены. Текст обращений и имена клиентов в отчёты не попадают. Живая доставка отчётов в MAX пока не проверена.

## Часть 11 — локальная Excel-выгрузка

Команда `stats --xlsx` создаёт самостоятельный `.xlsx` из того же результата, который используется текстовой сводкой. Нужна новая зависимость `openpyxl`; после обновления проекта выполните установку из `requirements.txt`.

```powershell

.\.venv\Scripts\python.exe -m app.main stats --period=week --xlsx=reports/week.xlsx
.\.venv\Scripts\python.exe -m app.main stats --from-date=2026-09-01 --to-date=2026-09-22 --user-id=99 --xlsx=reports/specialist-99.xlsx
```

Относительный путь считается от папки MAX-проекта, недостающие каталоги создаются. Абсолютный путь также поддерживается. Файл с уже существующим именем не перезаписывается, в том числе при одновременном запуске нескольких экспортов. Отчёт сначала полностью записывается во временный файл рядом с результатом, затем публикуется без перезаписи; используется локальная файловая система с поддержкой жёстких ссылок (например, NTFS). При ошибке временный файл удаляется. Сочетать `--xlsx` и `--json-output` нельзя.

На листе «Статистика» находятся период, часовой пояс, выбранный исполнитель, итоговые показатели и таблица по парам «чат — исполнитель». Для таблицы включены фильтр и закрепление заголовков. MAX ID записываются текстом для сохранения всех цифр; длительности — числами Excel с форматом `[h]:mm:ss`, поэтому не обнуляются после 24 часов. Отсутствующие измерения показываются пустыми ячейками, а не нулевой длительностью. В сводке без измерений указано «Нет данных».

Это снимок готовых расчётов, без формул и внешних ссылок: редактирование ячеек не пересчитывает сводку. Текст сообщений и имена клиентов не экспортируются. Ограничения и правила отбора совпадают с частью 10. Локальная команда не меняет схему базы; экспорт не создаёт заданий в outbox и не обращается к MAX.

Проверены повторное чтение XLSX, точность int64 ID, длительности больше суток, пустые данные, конкурентное создание файла и отсутствие частичного результата при сбое записи. Оформление проверено через визуальный предпросмотр; открытие в настольном Excel и загрузка XLSX в MAX ещё не проверялись. Отправка файла через мессенджер реализована в части 12.

## Часть 12 — Excel-отчёты в MAX

В рабочем чате доступны команды:

- `/stats_xlsx [day|week|month]` — общая статистика, только для администраторов.
- `/my_stats_xlsx [day|week|month]` — статистика самого отправителя, для специалистов и администраторов.
- Вместо периода можно указать две даты: `/stats_xlsx 2026-09-01 2026-09-22`.

По умолчанию выбирается текущий день в TIMEZONE. Файл приходит в рабочий чат: личная статистика означает фильтр по исполнителю, а не приватную доставку. Права и расчёты совпадают с текстовыми командами. Предел для команды — 10000 строк группировки и 20 МиБ готового файла; при превышении количества строк бот предлагает сократить период. Ошибка формирования или превышение размера отмечается как `failed` в очереди.

Снимок отчёта сохраняется в одной транзакции с обработкой команды. Файл формируется во временном каталоге, который удаляется после чтения; JSON снимка и токен загруженного вложения остаются в собственной базе MAX. Повтор события не создаёт второй отчёт. Миграция базы 8 → 9 добавляет поля очереди без удаления заданий.

Загрузка использует `POST /uploads?type=file`, затем multipart-поле `data` по полученному HTTPS URL. Токен бота на сервер загрузки не передаётся, перенаправления запрещены. Токен файла сохраняется до отправки сообщения; очередь выдерживает паузу 5 секунд для обработки файла MAX. Ошибка `attachment.not.ready` вызывает отложенную повторную отправку с тем же токеном. Ошибки загрузки допускают повтор, а неоднозначный результат отправки сообщения переводится в `uncertain` без автоматического повторения. После аварийной остановки задание `sending` требует проверки через существующие команды восстановления очереди.

Контракт сверен с [документацией загрузки файлов MAX](https://dev.max.ru/docs-api/use-cases/sending-messages/media). Автономные тесты проверяют права, дедупликацию, XLSX, миграцию, сохранение токена, задержку и повтор после перезапуска, ошибки загрузки и неопределённую отправку. Реальная загрузка XLSX и доставка в клиент MAX ещё требуют испытания с тестовым ботом.

## Часть 13 — напоминания о неназначенных заявках

Администратор бота настраивает напоминания в рабочем чате:

```text
/set_unassigned_reminder 60 1,2,3,4,5 08:00 17:00 30
/get_unassigned_reminder
/set_unassigned_reminder off
```

Пример включает проверку каждые 60 минут по понедельникам–пятницам с 08:00 включительно до 17:00 исключительно, для заявок старше 30 минут. Дни: 1 — понедельник, 7 — воскресенье. Интервал допускается от 1 до 10080 минут, порог возраста — от 1 до 525600 минут. Время строго `ЧЧ:ММ`; одинаковые начало и конец отклоняются. Часовой пояс берётся из `TIMEZONE`.

Ночные смены поддерживаются: `22:00 06:00` во вторник включает ночь до 06:00 среды. День недели относится к началу смены. Интервал между проверками рассчитывается по абсолютному времени, в том числе при переводе часов. После длительного простоя внутри разрешённых часов формируется один текущий список, без сообщений за каждый пропущенный интервал.

По умолчанию напоминания отключены. Настройки, номер рассылки и ближайшая проверка хранятся в SQLite; изменение настроек, ответ команды и запись аудита фиксируются вместе. Повтор уже обработанной команды не меняет расписание. При включении или изменении настроек первая проверка выполняется в ближайшем разрешённом окне; повтор тех же настроек не сбрасывает таймер.

Проверка выполняется обработчиком `run` после обработки входящих сообщений и нажатий. `process-inbox` также может создать задания, но ничего не отправляет; `serve` и `deliver-outbox` сами расписание не проверяют. В выборку входят только заявки `new` без исполнителя, возраст считается от первого сообщения, сохранённого ботом. Заявки в ожидании, в работе, закрытые и отменённые исключаются.

Сообщение содержит номера заявок, ID чатов, возраст и время снимка; длинный список разбивается на страницы без потери номеров. Статус заявки может измениться между формированием списка и доставкой. Часы ограничивают создание снимка; повторы доставки могут произойти позже. `off` прекращает создание новых рассылок, уже сохранённые задания остаются в очереди.

Прогресс расписания и все страницы outbox записываются одной транзакцией. Пока у предыдущей рассылки есть `pending`, `sending`, `failed` или `uncertain`, следующая не создаётся. Ошибки требуют обычного восстановления очереди; неопределённый результат отправки автоматически не повторяется. Если подходящих заявок нет, следующая проверка переносится на заданный интервал без отправки сообщения.

Миграция 9 → 10 добавляет таблицу `schedules`, сохраняя существующие задания и отчёты. Проверены роли, команды, границы времени и возраста, ночные смены, переход часов, перезапуск, конкурентная обработка, откат транзакции, длинные списки и миграция. Всего 124 автономных теста. Живое испытание расписания в MAX ещё не выполнено.

## Часть 14 — ежедневный дайджест заявок в работе

Администратор бота задаёт время и дни в рабочем чате:

```text
/set_daily_reminder 09:00 1,2,3,4,5
/get_daily_reminder
/set_daily_reminder off
```

Пример включает дайджест в 09:00 по понедельникам–пятницам в `TIMEZONE`. По умолчанию он отключён. Время задаётся строго `ЧЧ:ММ`, дни — числами 1–7 через запятую. Настройки сохраняются в базе, изменения доступны только администраторам бота в рабочем чате и записываются в аудит.

Как в Telegram-версии, дайджест содержит заявки `in_progress` с назначенным специалистом: номер, ID чата и исполнителя, время в работе. Для заявок без исполнителя используется отдельное расписание из части 13. Закрытые, отменённые и ещё ожидающие обращения не включаются. Отсутствующее или некорректное время начала показывается как «нет данных».

После указанного времени формируется один снимок за текущую местную дату. Если бот был выключен в 09:00 и запущен в 12:00 того же разрешённого дня, он сформирует дайджест при запуске. Пропущенные предыдущие дни не рассылаются. Пустая выборка также отмечается как выполненная проверка дня, но сообщение не отправляется; появившиеся позже заявки попадут в следующий дайджест.

Отметка даты и все страницы очереди записываются одной транзакцией. Перезапуск, одновременные обработчики, смена времени настройки и выключение с повторным включением не сбрасывают отметку уже проверенного дня. При повторном часе осенью рассылка не дублируется; если назначенная минута отсутствует весной, проверка выполняется в первую доступную минуту после неё. Откат системной даты не создаёт повторных снимков за уже проверенные даты.

Пока у предыдущего дайджеста есть недоставленная страница или ошибка, новый не создаётся. После восстановления очереди бот может подготовить снимок за текущий разрешённый день. Настройка `off` останавливает создание новых дайджестов, но не удаляет уже сохранённые задания. В сообщении указано время снимка: фактическая доставка может быть позже, когда статусы заявок уже изменились.

Проверки встроены в `run` и `process-inbox` после обработки входящей очереди; `process-inbox` только создаёт задания. Миграция 10 → 11 добавляет отметку `last_run_date` к расписаниям и сохраняет предыдущие настройки и очередь. Проверены роли, фильтрация заявок, календарь, DST, перезапуск, конкурентная обработка, откат, пагинация, доставка через имитацию MAX и миграция. Всего 134 автономных теста; живое испытание ещё предстоит.

## Часть 15 — объявления в новых клиентских карточках

Команды доступны администраторам бота в рабочем чате:

```text
/set_notice - - Возможны задержки ответа технической поддержки.
/set_notice 2026-10-01T18:00 17:00-08:00 Вечером обращения обрабатываются дежурным специалистом.
/get_notice
/del_notice 2
/del_notice all
```

Формат: `/set_notice <срок или -> <интервал или -> <текст>`. Срок — будущая дата `ГГГГ-ММ-ДДTЧЧ:ММ` в `TIMEZONE`; `-` означает без срока. Интервал — `ЧЧ:ММ-ЧЧ:ММ` ежедневно, начало включительно, конец исключительно; `-` означает круглосуточно. Ночные интервалы поддерживаются. Одинаковые начало и конец отклоняются. При переводе часов дата окончания должна существовать и быть однозначной: для пропущенной или повторяющейся минуты команда попросит другое время.

Можно сохранить до 10 объявлений по 300 символов UTF-16 каждое (эмодзи обычно занимают две единицы). Благодаря этому все активные объявления помещаются в клиентскую карточку без обрезки. Текст может содержать переносы строк и отправляется без HTML/Markdown-разметки. `/get_notice` показывает все сохранённые объявления, включая истёкшие, отдельными сообщениями; ненужные удаляются по ID или все сразу. Сроки и интервалы видны в списке.

Как в Telegram-версии, объявления сопровождают клиентскую карточку заявки `new`, а не рассылаются отдельно по таймеру. Они выбираются при формировании задания карточки после окончания ожидания специалиста. Рабочая карточка остаётся без объявлений. При переходе заявки в работу, закрытии или отмене очередное обновление клиентской карточки убирает объявления.

Снимок текста сохраняется в outbox: истечение срока или удаление объявления не меняет уже подготовленную карточку и её повторы доставки. Ранее отправленные карточки по расписанию не редактируются. Поэтому время фактического показа может быть позже заданного интервала при задержке очереди; настройки применяются к следующим новым карточкам. Отправка объявления сама по себе не создаёт отдельных сообщений клиентам.

Команда, изменение базы, запись аудита и ответ фиксируются транзакционно; повтор входящего события не создаёт второе объявление. Текст объявления остаётся в собственной базе MAX. Миграция 11 → 12 добавляет таблицу `announcements`, сохраняя заявки, очередь и расписания. Проверены права, дедупликация, откат, срок действия, дневные/ночные границы, DST, сохранность снимка, лимиты UTF-16, доставка через имитацию API и миграция. Всего 142 автономных теста; живая проверка MAX ещё предстоит.

## Часть 16 — автоочистка сообщений бота

Команды администратора в рабочем чате:

```text
/set_autoclean 23:00 1,2,3,4,5,6,7
/get_autoclean
/set_autoclean off
```

По умолчанию автоочистка отключена. Время задаётся строго `ЧЧ:ММ`, дни — числами 1–7 через запятую. Используется `TIMEZONE`. После назначенного времени формируется один набор заданий за текущий разрешённый день, в том числе при запуске после простоя; пропущенные дни не воспроизводятся. Настройки и отметка даты сохраняются в SQLite и переживают перезапуск. Повторное включение в уже проверенный день не формирует второй набор.

Очистка возможна, только когда нет заявок `waiting`, `new`, `in_progress` и необработанных входящих сообщений/нажатий. Эти условия проверяются при создании заданий и перед захватом каждого задания для DELETE. Появление новой заявки приостанавливает оставшиеся удаления; уже начатый HTTP-запрос отменить этим условием нельзя. Если к назначенному времени есть открытые заявки, бот повторно проверяет возможность очистки позже в тот же день.

Цели выбираются исключительно из подтверждённых отправок outbox с известным `message_id`: карточки закрытых/отменённых заявок, ответы команд, отчёты, дайджесты и напоминания. Исходные сообщения клиентов не выбираются. Сообщения с неопределённой доставкой сначала требуют восстановления очереди. История заявок, тексты и исходные события в базе не удаляются: у отправленного сообщения записывается `deleted_at_ms`. Уже удалённая запись не ставится на удаление повторно. Сообщения, отправленные после формирования набора, попадут в следующий запуск очистки.

Удаление проходит через общую очередь с ограничением не чаще одной операции в секунду в чат. Проверяется сохранённый ID и версия исходной отправки; изменение цели даёт `failed` с причиной `delete_target_changed`. `off` приостанавливает захват уже подготовленных удалений, сохраняя их для последующего включения. Приостановленные удаления не блокируют обычную доставку. Повторы могут выполняться позже времени расписания, пока очистка включена и условия допускают удаление.

Контракт: [DELETE /messages в MAX](https://dev.max.ru/docs-api/methods/DELETE/messages). Боту нужны права администратора на удаление сообщений. Успехом считается только `success=true`. Сетевые ошибки, HTTP 429 и 5xx повторяются с задержкой; после предела попыток задание остаётся `failed`. HTTP 403/404 и отрицательное подтверждение не считаются успешным удалением и требуют разбора. Прерванный `sending` не повторяется автоматически после перезапуска.

Восстановление использует существующие команды. `queue-inspect` показывает `delete_mid` и `delete_source_id`. Для повтора DELETE с тем же ID не требуется подтверждение отсутствия доставки:

```powershell
.\.venv\Scripts\python.exe -m app.main queue-retry --job-id=123 --revision=0 --reason="Повтор удаления после сбоя сети"
```

Если оператор проверил отсутствие сообщения в MAX, можно подтвердить удаление без `--message-id`:

```powershell
.\.venv\Scripts\python.exe -m app.main queue-confirm --job-id=123 --revision=0 --delivered-revision=0 --reason="Отсутствие сообщения проверено в MAX"
```

В примерах 123 — ID задания удаления из `queue-inspect`, а не ID заявки. Подтверждение записывается в аудит и отмечает исходную отправку удалённой. Команды восстановления сами не обращаются к MAX.

Миграция 12 → 13 добавляет поля удаления в outbox, сохраняя очередь, заявки и расписания. Формирование заданий и отметка календарного дня транзакционны. Проверены права, миграция, границы времени, перезапуск, выбор целей, успешное удаление, сетевые/API-ошибки, блокировка открытыми заявками, отсутствие блокировки обычной доставки и ручное восстановление. Всего 151 автономный тест. Живое удаление и права конкретного MAX-бота ещё не проверены.

## Часть 17 — помощь, меню и списки заявок

В настроенных клиентских чатах и рабочем чате доступны `/start`, `/help`, `/menu`, `/whoami`. Команды не создают заявку и не отменяют ожидание ответа сотрудника. `/whoami` показывает собственный MAX ID, ID текущего чата и роли из базы бота. Меню содержит кнопки навигации и справку по доступным командам.

В клиентском чате `/my_requests [страница]` показывает обращения самого отправителя в этом чате, включая завершённые и отменённые. Чужие обращения и обращения из других чатов исключаются. Ответ отправляется в тот же групповой чат и виден его участникам: фильтр по автору не означает приватную доставку. Тексты исходных обращений в список не включаются.

Специалисты и администраторы в рабочем чате используют:

- `/open_requests [страница]` — заявки `waiting`, `new`, `in_progress`;
- `/open_unassigned_requests [страница]` — заявки `new` без исполнителя;
- `/my_active_requests [страница]` — заявки `in_progress`, назначенные отправителю.

Списки содержат номера, статусы и, в рабочем чате, ID чата и исполнителя. На странице не более 10 заявок, новые номера идут первыми. Например, `/open_requests 2` открывает вторую страницу. Номер страницы — не ID другого пользователя; личную выборку нельзя переключить на чужого исполнителя. Каждая команда читает текущее состояние базы, поэтому при новых заявках состав страниц может меняться.

Кнопки открывают первую страницу соответствующего списка. Каждое меню привязано к пользователю и чату, для которых оно отправлено; другой участник должен вызвать собственное `/menu`. Проверяются сохранённый `mid`, наличие выбранной кнопки в исходном меню и актуальные роли. Отзыв роли закрывает доступ и через ранее отправленные кнопки. Удалённые автоочисткой меню не обрабатываются. Принятое нажатие получает ответ через очередь callback, результат команды — отдельным сообщением.

Изменение статуса заявки по-прежнему выполняется кнопками её карточки; меню и списки только читают данные. Полномочия взять/завершить заявку остаются у роли специалиста. Пошаговые диалоги и команда `/cancel` для отмены таких диалогов в этой части не добавлены. Работа в неизвестных чатах и личных диалогах без `chat_id` по-прежнему не поддерживается; автоматическая регистрация списка команд в MAX не выполняется.

Ответы и отметка обработки события сохраняются одной транзакцией. Повтор события или callback не создаёт второй ответ. Миграция 13 → 14 добавляет `menu_owner` в outbox с сохранением существующих заданий. Проверены права, фильтрация по автору/чату/исполнителю, пагинация, доставка клавиатуры, привязка меню, отзыв ролей, дедупликация, откат и миграция. Всего 159 автономных тестов; живые кнопки MAX ещё требуют проверки.

## Часть 18 — полный сохранённый текст обращения

```text
/request 123
/request 123 2
```

Первая команда открывает первую страницу заявки №123, вторая — вторую. Подсказка добавлена в помощь и списки заявок. Клиент может открыть только свою заявку в текущем настроенном клиентском чате. Специалист или администратор бота может открыть заявку в рабочем чате; роль проверяется при каждой команде. Для чужой и несуществующей заявки возвращается одинаковый ответ без раскрытия содержимого. В неизвестных чатах команда не отвечает.

Показываются статус и все сообщения, сохранённые в `request_messages` при сборе обращения, в порядке получения. Это не вся последующая переписка в группе: сообщения, которые основной обработчик не прикрепил к заявке, здесь не появляются. В рабочем чате также показываются ID чата, автора и назначенного исполнителя. Если у старой заявки нет сохранённых исходных сообщений, бот сообщает об этом явно.

Текст не обрезается и не интерпретируется как HTML/Markdown. Каждая команда выдаёт одну страницу, до 3000 единиц UTF-16 исходного представления плюс заголовок и подсказка следующей страницы, в пределах лимита MAX. Разбиение сохраняет все символы, включая эмодзи; длинное сообщение может продолжиться на следующей странице. Страницы строятся из текущего сохранённого содержимого: если во время ожидания к обращению добавилось сообщение, число страниц может увеличиться.

У вложений перечисляются только типы; токены загрузки, служебные URL и весь JSON события не выводятся. Текст связанного/пересланного сообщения показывается, если он сохранён в событии; иначе выводится соответствующая отметка. Передача самих файлов ещё не реализована. Ответ публикуется в том же чате и виден его участникам — это не приватная доставка.

Проверка доступа выполняется до чтения исходных сообщений. Ответ и обработка команды фиксируются транзакционно, повтор события не создаёт дубль. Схема базы остаётся 14. Проверены роли и их отзыв, автор и чат, сохранение длинного текста и эмодзи, несколько сообщений, границы страниц, скрытие служебных полей вложений, откат и доставка через имитацию API. Всего 165 автономных тестов; живая проверка MAX ещё предстоит.

## Часть 19 — административные действия над заявками

Только администратор бота в рабочем чате может выполнять:

```text
/assign_request 123 99
/cancel_request 123 Ошибочно созданная заявка
/close_all
```

`/assign_request <заявка> <MAX ID>` назначает существующего специалиста из ролей бота. Новая заявка `new` переходит в `in_progress`, записывается время начала работы. Если заявка уже в работе, исполнитель меняется с сохранением исходного времени начала, как при `/reassign`. Повторное назначение того же исполнителя не меняет версию заявки. Роли администратора без роли специалиста недостаточно для назначения исполнителем. Ожидающие, закрытые и отменённые заявки назначить нельзя.

`/cancel_request <заявка> <причина>` отменяет заявку `waiting`, `new` или `in_progress`, записывает время окончания и причину до 300 символов в журнале управления. Отменённая заявка не считается закрытой в статистике. Если клиентская карточка ещё не создавалась на стадии ожидания, новая карточка отмены не отправляется; администратор получает ответ команды. Для уже существующих карточек статус обновляется и кнопки действий убираются.

`/close_all` сразу закрывает все заявки `new` и `in_progress`, без дополнительного диалога. Это соответствует массовому закрытию Telegram-версии. Заявки `waiting` остаются без изменений; закрытые и отменённые повторно не изменяются. В журнале сохраняется запись по каждой затронутой заявке. Закрытые таким способом новые заявки входят в число завершённых в статистике, но без отсутствующих измерений времени работы и исполнителя.

Перед каждой командой проверяется актуальная роль администратора. Изменения статуса, ревизии, времени, журнал, ответ и обновления карточек фиксируются в одной транзакции. Повтор входящего события не применяет действие второй раз. Известные `mid` карточек сохраняются для редактирования; `failed`, `uncertain` и прерванные отправки автоматически не сбрасываются. Старые кнопки с предыдущей ревизией больше не меняют заявку.

Схема базы остаётся 14. Проверены права, валидация ID и ролей, начальное назначение и переназначение, отмена разных состояний, массовое закрытие, повторы, аудит, откат при сбое и сохранение ID/проблемных состояний очереди. Всего 171 автономный тест. Живые административные действия в MAX ещё не проверены.

## Локальный запуск приёмника

В `.env` задайте `WEBHOOK_SECRET`: случайный секрет из 5–256 латинских букв, цифр, `_` или `-` (рекомендуется не менее 32 символов). Тот же секрет впоследствии используется при регистрации подписки MAX.

```powershell
.\.venv\Scripts\python.exe -m app.main serve
```

По умолчанию слушает `127.0.0.1:8080`; адрес меняют `LISTEN_HOST` и `LISTEN_PORT`. При запуске создаётся собственная база по `DATABASE_PATH`. Остановка — Ctrl+C.

| Маршрут | Назначение |
| --- | --- |
| `POST /webhook/max` | JSON события, заголовок `X-Max-Bot-Api-Secret`, тело до 1 МиБ |
| `GET /healthz` | Процесс отвечает |
| `GET /readyz` | База доступна; ответ содержит `mode: collect_only` |

Для настоящих событий необходим reverse proxy: публичный HTTPS на порту 443 с доверенным сертификатом, перенаправляющий запросы на локальный приёмник. Требования указаны в [документации подписок MAX](https://dev.max.ru/docs-api/methods/POST/subscriptions). Подписка автоматически не регистрируется. Успех `/readyz` подтверждает доступность хранилища, но не готовность полного сценария бота.

На Windows сервер использует SelectorEventLoop для обхода обнаруженной ошибки закрытия TCP-соединений Proactor в локальном Python 3.12. Это вариант для локальных испытаний с небольшой нагрузкой; промышленную нагрузку и публичный HTTPS ещё предстоит проверить.
