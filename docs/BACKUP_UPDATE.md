# Резервное копирование и подготовка обновления

Реализованы создание, проверка и восстановление комплекта в новый каталог, а также `scripts/update.sh` для обновления службы. Автоматическая подмена рабочей базы не выполняется. Реальные испытания на Linux ещё не проведены.

## Обновление установленной службы

Скачайте выбранную доверенную версию проекта в отдельный каталог. Остановите все вручную запущенные обработчики и команды, изменяющие базу; скрипт управляет только штатной службой systemd. Из каталога новой версии выполните:

```bash
sudo bash scripts/update.sh
```

Нужна завершённая установка через `install.sh` на Debian 13 или Ubuntu 24.04. Скрипт отказывается от изменённых unit, дополнительных drop-in и нестандартного пути базы. Два обновления одновременно блокируются через `flock`.

1. Код копируется в новый `/opt/max-ts-ticket-bot/releases/release_XXXXXXXX`. Окружение Python создаётся сразу по окончательному пути; текущая служба продолжает работать во время установки зависимостей.
2. Проверяются профиль и доступ к API от имени пользователя службы. Затем служба останавливается и её остановка подтверждается.
3. В `/var/backups/max-ts-ticket-bot/release_XXXXXXXX` создаётся проверенная копия базы, профиля, **предыдущего** кода и unit.
4. Unit переключается на новую версию. Штатный запуск приложения применяет миграции и запускает обработчики; скрипт проверяет `/readyz` и состояние systemd.

Настройки, роли и путь базы сохраняются. HTTPS и подписка MAX не меняются. Старые каталоги и копии не удаляются автоматически.

При ошибке до остановки текущая служба продолжает работать. При ошибке после остановки потребуется разбор состояния; если новая служба уже запускалась, скрипт останавливает её. Не возвращайте старую базу автоматически: новая версия могла успеть принять события или отправить сообщения. Сначала сохраните текущее состояние, проверьте журналы и комплект копии. При аварийном завершении самого скрипта также проверьте состояние службы; незавершённый файл `max-ts-ticket-bot.service.update` нужно осмотреть перед повторным запуском.

```bash
sudo systemctl status max-ts-ticket-bot.service
sudo journalctl -u max-ts-ticket-bot.service -n 100 --no-pager
systemctl show max-ts-ticket-bot.service --property=WorkingDirectory --value
```

После обновления выполняйте административные Python-команды из каталога `WorkingDirectory`, используя **его** `.venv/bin/python`. Путь `/opt/max-ts-ticket-bot/.venv/bin/python` относится к первой установленной версии и больше не является текущим.

## Создать и проверить копию

На установленном сервере из каталога приложения:

```bash
cd /opt/max-ts-ticket-bot
sudo .venv/bin/python -m app.backup create --profile /etc/max-ts-ticket-bot/config.json --unit /etc/systemd/system/max-ts-ticket-bot.service --output /var/backups/max-ts-ticket-bot/before-update-001
sudo .venv/bin/python -m app.backup verify --bundle /var/backups/max-ts-ticket-bot/before-update-001
```

Каталог результата должен быть новым. Копия содержит:

- согласованный снимок собственной базы MAX через SQLite Backup API, включая зафиксированные данные WAL;
- `config.json` с настройками и секретами;
- Python-код текущего приложения и `requirements.txt` для восстановления совместимой версии;
- дополнительный CA PEM из профиля, если он настроен;
- unit службы, если указан `--unit`;
- `manifest.json` с версией схемы, временем создания и SHA-256 каждого файла.

Копируется код той версии, из каталога которой запущена команда. Запускайте резервное копирование из установленного приложения до замены его кода. Копия не содержит venv: окружение восстанавливается из зависимостей. Конфигурации Nginx, systemd drop-in, сертификат HTTPS и его приватный ключ не входят в комплект; сохраняйте их отдельно по правилам сервера.

Копия содержит токен бота и секрет Webhook — она не предназначена для GitHub или публикации. На Linux каталог создаётся с режимом 0700, файлы — 0600; Windows-проверки не подтверждают применение этих прав на сервере. Контрольные суммы обнаруживают порчу, но не являются подписью и не удостоверяют происхождение комплекта: используйте свои доверенные копии.

Для обычной резервной копии бот может продолжать работать: Backup API получает согласованный снимок базы, без простого копирования одного `.db` поверх активного WAL. Новые события после снимка в эту копию не входят. Настройки и код не должны меняться во время копирования. Для копии непосредственно перед миграцией сначала остановите службу и все ручные процессы, работающие с этой базой.

Команда проверяет идентификатор приложения MAX, поддерживаемую версию схемы и `PRAGMA quick_check`, затем контрольные суммы. Чужая база, включая Telegram, не принимается. При сбое до публикации временный комплект удаляется; при прерванном сохранении результата может остаться неполный каталог, который нельзя использовать без успешного `verify`. Занятое имя результата не перезаписывается.

## Пробное восстановление

```bash
sudo .venv/bin/python -m app.backup restore --bundle /var/backups/max-ts-ticket-bot/before-update-001 --output /var/backups/max-ts-ticket-bot/restore-check-001
```

Восстановление сначала проверяет комплект и распаковывает только перечисленные файлы в новый каталог; затем снова проверяет результат. Ссылки и пути за пределы каталога запрещены. При сбое остаётся отметка `INCOMPLETE`. Работающая база не открывается на запись и не подменяется.

Не запускайте восстановленный код сразу со старым `config.json`: пути базы и CA в нём сохранены как в исходной установке и могут указывать на рабочие данные. Для теста задайте отдельную базу из восстановленного каталога, проверьте пути и используйте изолированные тестовые настройки. Исходный профиль сохраняется буквально, без автоматического изменения токена, путей и ролей.

## Принципы обновления и ручного восстановления

1. Получить выбранную версию из GitHub в отдельный каталог, проверить код и зависимости. Не использовать повторный `install.sh` как обновление.
2. Подготовить новое venv в конечном каталоге версии; не переносить готовый venv с абсолютными путями. Проверить совместимость профиля и Python до остановки старого приложения.
3. Остановить службу и все ручные обработчики; подтвердить остановку. При временно недоступном Webhook MAX может повторять доставку в пределах своих лимитов — длительное обслуживание требует отдельного плана.
4. Создать и проверить комплект старого кода, базы, настроек и фактического unit. Дополнительно сохранить reverse proxy, drop-in и HTTPS-сертификаты. Зафиксировать, какая версия обслуживала эту базу.
5. Выполнить миграцию новой версией только после проверки копии, переключить службу на подготовленный каталог и проверить systemd, `/readyz`, очередь, Webhook и тестовое обращение.
6. Если новая версия ещё не принимала события, откатывать согласованную пару старого кода и снимка базы при полностью остановленных процессах. При замене SQLite изолировать старые `.db`, `-wal` и `-shm` вместе; не оставлять чужие WAL-файлы рядом с восстановленной базой. Сохранить текущие файлы отдельно, восстановить владельца и права службы.
7. Если новая версия уже принимала события или отправляла сообщения, не заменять базу автоматически старым снимком: сначала сохранить новое состояние и разобрать поступившие изменения и незавершённые отправки. Откат базы не отменяет сообщения, отправленные в MAX, и может привести к повторам.

Обновление автоматизировано командой выше. Ручное восстановление требует отдельной проверки совместимости кода и базы. Регулярный backup реализован ниже; срок хранения и внешнее хранилище копий остаются в плане.

## Ежедневные резервные копии

Правила ручной очистки описаны в разделе «Хранение и очистка» ниже; таймер сам ничего не удаляет.

Первоначальный `install.sh` устанавливает таймер автоматически после успешного запуска бота. Для уже установленного бота из новой версии проекта выполните:

```bash
sudo bash scripts/install-backup.sh
```

Установщик создаёт проверенную пробную копию и только после успешного завершения включает `max-ts-ticket-bot-backup.timer`. Повторный запуск создаёт ещё одну копию. Настройки расписания в drop-in сохраняются.

Каждый день с 03:00 до 03:15 по часовому поясу **сервера** создаётся каталог `scheduled_...` в `/var/backups/max-ts-ticket-bot`. Часовой пояс бота в JSON не меняет расписание systemd. Пропущенный во время выключения запуск выполняется после включения таймера. Ошибка копирования отмечается как сбой службы и записывается в журнал; немедленный автоматический повтор не предусмотрен.

Бот продолжает работать: SQLite Backup API сохраняет согласованный снимок с учётом WAL. Скрипт определяет текущий `WorkingDirectory` службы и использует код и окружение этой версии. Общая с обновлением блокировка предотвращает копирование во время переключения версии; если за 60 секунд блокировка не освободится, задание завершается ошибкой. Во время копирования не изменяйте профиль вручную.

Копии доступны только root и содержат секреты. Старые копии **не удаляются**: контролируйте свободное место. Копирование на другой сервер и проверка восстановления остаются отдельными задачами. Nginx, сертификаты и drop-in в комплект не входят.

```bash
systemctl list-timers max-ts-ticket-bot-backup.timer
sudo journalctl -u max-ts-ticket-bot-backup.service -n 50 --no-pager
sudo systemctl start max-ts-ticket-bot-backup.service
```

Чтобы поменять время, выполните `sudo systemctl edit max-ts-ticket-bot-backup.timer` и добавьте:

```ini
[Timer]
OnCalendar=
OnCalendar=*-*-* 04:00:00
```

Затем `sudo systemctl daemon-reload` и `sudo systemctl restart max-ts-ticket-bot-backup.timer`. Для отключения расписания: `sudo systemctl disable --now max-ts-ticket-bot-backup.timer`. Это не удаляет копии и не останавливает уже выполняющееся копирование.

Синтаксис Bash и существующая логика копирования проверены локально. Запуск таймера, ограничения прав systemd и восстановление после перезагрузки требуют испытания на Debian/Ubuntu.

## Хранение и очистка

Команда `app.backup_retention` предназначена для Linux. Запускайте из текущего `WorkingDirectory` службы, используя Python этой версии (после обновления это каталог в `releases`). По умолчанию команда только показывает кандидатов:

```bash
sudo .venv/bin/python -m app.backup_retention --keep 7 --days 30
```

Удаление включается отдельно:

```bash
sudo .venv/bin/python -m app.backup_retention --keep 7 --days 30 --apply
```

Оба условия должны выполняться одновременно: копия старше 30 суток **и** не входит в последние 7 исправных плановых копий. Возраст вычисляется по UTC-дате `created_at` в manifest; граница ровно 30 суток сохраняется. Параметры должны быть положительными целыми числами.

Обрабатываются только непосредственные каталоги вида `scheduled_YYYYMMDDTHHMMSSZ_число`. Копии `release_...` перед обновлением и вручную названные комплекты сохраняются. Повреждённые, неполные, содержащие ссылки, неподдерживаемые или датированные будущим комплекты пропускаются и не засчитываются в число исправных копий. Если исправных копий не больше `--keep`, удаления не будет.

Перед удалением каждый комплект повторно проверяется; удаляются только его проверенные файлы и пустые каталоги. Ошибка прерывает очистку, поэтому часть выбранных копий может остаться удалённой, а текущий комплект — неполным. Следующий запуск сохранит такой комплект для ручного разбора. Работающая база не затрагивается.

Предпросмотр и очистка используют ту же блокировку, что обновление и таймер; при занятости завершаются ошибкой. Запускайте команды по очереди и не меняйте файлы копий вручную во время очистки. Для отдельного каталога используйте `--directory /абсолютный/путь`.

Расписание автоматической очистки не включено. Перед освобождением места проверьте возможность восстановления и наличие внешней копии.
