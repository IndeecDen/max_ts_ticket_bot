# Первоначальная установка MAX на Linux

Установщик входит в релиз 1.0.5. Работа службы, обновление с сохранением профиля и базы, создание и проверка резервной копии подтверждены на Debian 13. Чистая установка Ubuntu 24.04, восстановление и перезагрузка ОС требуют отдельных испытаний. HTTPS и регистрация Webhook выполняются по инструкции ниже.

## Подготовка

Установщик принимает Debian 13 и Ubuntu 24.04 с настоящим systemd, доступом sudo/root и сетью для APT, PyPI и MAX. Используется системный Python: [Debian 13 поставляет Python 3.13](https://www.debian.org/News/2025/20250809), [Ubuntu 24.04 — Python 3.12](https://ubuntu.com/developers/docs/reference/availability/python/). Совместимость всего приложения с обоими выпусками ещё требует серверной проверки. Другие версии установщик отклоняет до установки пакетов.

Создайте MAX-бота, получите токен, ID рабочего чата специалистов и MAX ID хотя бы одного администратора бота. Добавьте бота в нужные групповые чаты с необходимыми правами: они автоматически считаются клиентскими, кроме рабочего чата. Сохраните полный проект из [GitHub](https://github.com/IndeecDen/max_ts_ticket_bot) на сервер. Скрипт запускается из полученного проекта и не использует Telegram-проект.

## Запуск мастера

В каталоге проекта выполните:

```bash
sudo bash scripts/install.sh
```

Справка без установки:

```bash
bash scripts/install.sh --help
```

Скрипт проверит ОС/systemd и занятость целевых путей, установит Python/venv, CA-сертификаты и tzdata, создаст отдельного системного пользователя `max-ts-ticket-bot`, скопирует только код приложения и установит закреплённые зависимости в venv. Токены, база и `.env` из исходной папки не копируются.

Мастер последовательно запросит:

1. MAX-токен — скрытый ввод.
2. Рабочий чат, начальных администраторов и специалистов; несколько ID сотрудников вводятся через запятую. Начальный администратор обязателен; список специалистов может быть пустым. Клиентские чаты не запрашиваются: мастер сохраняет `policy.auto_client_chats: true`.
3. Часовой пояс, ожидание ответа специалиста, локальный HTTP-порт и таймаут запросов к MAX.
4. Необязательный абсолютный путь к доверенному CA PEM. Сертификат должен читаться службой и находиться вне `/home` и `/root`, скрытых для службы. Для дополнительного CA подойдёт `/etc/max-ts-ticket-bot/ca.pem` с доступом группы службы. Проверка TLS не отключается.
5. Секрет Webhook — скрытый ввод; Enter генерирует новый секрет.
6. Публичный HTTPS URL Webhook — можно оставить пустым и подготовить позже.

При ошибке данные не сохраняются, мастер предложит повторить ввод. Ctrl+C прерывает настройку. Профиль — JSON, а не shell-скрипт: специальные символы токена не выполняются как команды. Существующий профиль проверяется и не перезаписывается. Установка с уже занятыми чужими путями или unit останавливается.

## Что устанавливается

| Путь | Назначение |
| --- | --- |
| `/opt/max-ts-ticket-bot` | Код и `.venv`, владелец root |
| `/etc/max-ts-ticket-bot/config.json` | Настройки и секреты, root:группа службы, режим 0640 |
| `/var/lib/max-ts-ticket-bot` | Собственная SQLite-база MAX и блокировки, режим 0700 |
| `/etc/systemd/system/max-ts-ticket-bot.service` | Служба systemd |

Профиль хранит также список чатов и начальные роли, которые раньше приходилось передавать при каждом запуске. В режиме `--profile` настройки не читаются из `.env` и переменных окружения. Роли после первичной инициализации остаются в базе; профиль не сбрасывает последующие назначения и отзывы ролей.

Перед запуском скрипт от имени пользователя службы выполняет `check-config` и читающий `check-api`. Неверный токен, недоступный чат или отсутствие необходимых прав прерывают установку до включения службы. Затем устанавливается unit, выполняются `daemon-reload` и `enable --now`, проверяются локальный `/readyz` и состояние systemd. Локальная готовность не подтверждает работу публичного Webhook.

Служба запускается без root, с перезапуском после ошибки и ограничением серии запусков. Постоянная запись разрешена в каталоге данных; временные файлы создаются в отдельном временном пространстве службы. После включения unit systemd должен запускать его при загрузке ОС — проверка реальной перезагрузки пока не выполнена.

## Что ещё нужно для сообщений из MAX

Публичный URL в JSON используется отдельной командой настройки Webhook. Установщик не меняет конфигурацию reverse proxy, DNS, firewall и подписки MAX. Нужно подготовить доверенный HTTPS на порту 443 и перенаправление `/webhook/max` на `127.0.0.1:<LISTEN_PORT>`, затем зарегистрировать подписку с секретом из профиля и проверить тестовое событие. Не публикуйте профиль и секреты в GitHub или диагностических сообщениях. Справка: [подписки MAX](https://dev.max.ru/docs-api/methods/POST/subscriptions).

## Управление и диагностика

```bash
sudo systemctl status max-ts-ticket-bot.service
sudo journalctl -u max-ts-ticket-bot.service -n 100 --no-pager
sudo systemctl restart max-ts-ticket-bot.service
sudo systemctl stop max-ts-ticket-bot.service
sudo systemctl disable --now max-ts-ticket-bot.service
```

Проверка профиля после ручного редактирования:

```bash
cd /opt/max-ts-ticket-bot
sudo -u max-ts-ticket-bot .venv/bin/python -m app.main check-config --profile /etc/max-ts-ticket-bot/config.json
sudo -u max-ts-ticket-bot .venv/bin/python -m app.main queue-status --profile /etc/max-ts-ticket-bot/config.json
```

Менять настройки следует через `sudoedit /etc/max-ts-ticket-bot/config.json`; после проверки перезапустите службу. Изменение начальных ролей в профиле не заменяет управление ролями в базе.

Если первая установка прервалась при зависимостях или настройке, повторный запуск продолжает работу с уже скопированным кодом и сохраняет профиль. Если служба уже запущена, скрипт не изменяет её; при ошибке готовности сначала посмотрите журналы. Для продолжения незавершённой установки остановите службу после разбора ошибки и повторите скрипт. Успешно завершённую установку повторный запуск не обновляет: он проверяет состояние службы и оставляет код, конфигурацию и базу на месте.

Для обновления используйте `scripts/update.sh` из новой версии проекта: [инструкция](BACKUP_UPDATE.md). Не используйте повторную установку как обновление. Автоматический откат базы, удаление файлов установки и автоконфигурация HTTPS не выполняются.


## Подготовка HTTPS и регистрация подписки (часть 21)

Нужны домен с DNS-записью на сервер, доступный TCP 443 и сертификат доверенного центра с полной цепочкой. В `public_webhook_url` профиля укажите, например, `https://ваш-домен/webhook/max`, без явного порта. Используйте реальный ASCII-домен (для международного имени — punycode). В этой версии путь допускает буквы, цифры, `/`, `_` и `-`. Выпуск и продление сертификата пока настраиваются отдельно; самоподписанный сертификат не подходит.

При уже настроенном reverse proxy направьте именно этот публичный путь на `http://127.0.0.1:<LISTEN_PORT>/webhook/max`, сохранив заголовок `X-Max-Bot-Api-Secret`. Не выставляйте наружу `/readyz` и другие внутренние маршруты.

Для отдельного виртуального хоста Nginx можно сгенерировать конфигурацию из профиля. В примере PEM уже получены и находятся в указанных путях; генератор их не выпускает:

```bash
cd /opt/max-ts-ticket-bot
sudo .venv/bin/python -m app.setup_webhook nginx --profile /etc/max-ts-ticket-bot/config.json --certificate /etc/ssl/max/fullchain.pem --key /etc/ssl/max/privkey.pem --output /etc/nginx/sites-available/max-ts-ticket-bot
```

Предварительно установите Nginx, если он ещё не используется на сервере. Просмотрите созданный файл и проверьте отсутствие другого виртуального хоста с тем же доменом. Генератор не изменяет существующие файлы, не создаёт ссылку и не перезапускает Nginx. После проверки настройте ссылку и примените конфигурацию:

```bash
sudo ln -s /etc/nginx/sites-available/max-ts-ticket-bot /etc/nginx/sites-enabled/max-ts-ticket-bot
sudo nginx -t
sudo systemctl reload nginx
```

Для ещё не запущенного Nginx после успешного `nginx -t` используйте `sudo systemctl enable --now nginx`. Сгенерирован только HTTPS-хост, получение сертификата и ACME-маршрут в него не входят. Nginx на Linux в текущей среде не запускался — его собственная проверка обязательна перед применением.

Проверка маршрута без изменения подписок:

```bash
cd /opt/max-ts-ticket-bot
sudo -u max-ts-ticket-bot .venv/bin/python -m app.setup_webhook check --profile /etc/max-ts-ticket-bot/config.json
```

Команда проверяет TLS без перенаправлений, отправляет `{}` без секрета и ожидает отказ 401, затем с секретом — ошибку невалидного события 400. Тестовые заявки и записи inbox не создаются; токен MAX на endpoint не передаётся. Эта проверка с сервера не заменяет проверку доступности со стороны MAX.

Регистрация после успешной проверки:

```bash
sudo -u max-ts-ticket-bot .venv/bin/python -m app.setup_webhook register --profile /etc/max-ts-ticket-bot/config.json
```

Команда снова проверяет HTTPS, читает подписки, создаёт или обновляет подписку на `message_created` и `message_callback`, передаёт секрет и сверяет результат повторным чтением. Основание: [POST /subscriptions](https://dev.max.ru/docs-api/methods/POST/subscriptions), [GET /subscriptions](https://dev.max.ru/docs-api/methods/GET/subscriptions). При другой подписке или дублях команда останавливается и ничего не удаляет. Перенос с другого адреса нужно разбирать отдельно.

Хэши подтверждённых настроек и ответа MAX сохраняются в `bot_meta`; одинаковый повторный запуск пропускает POST. Смена секрета/токена/параметров или изменение списка подписок вызывает повторную настройку того же URL. После таймаута нет слепого автоматического повтора в том же запуске: устраните причину и запустите команду снова для сверки. Одновременные запуски на одной базе защищены отдельной файловой блокировкой. Неизвестные внешние изменения секрета нельзя надёжно установить только чтением списка MAX; окончательно проверьте реальное событие.

Обычный запуск службы и `install.sh` пока не регистрируют подписку автоматически — это отдельный шаг после подготовки DNS/HTTPS. В текущей сессии реальные подписки и конфигурация Nginx не изменялись.


Резервные копии базы, профиля и кода, ежедневный таймер, а также обновление службы: [руководство](BACKUP_UPDATE.md). Установщик включает таймер после проверенной пробной копии. Повторный запуск установщика сохраняет код/базу, переустанавливает управляемые файлы backup и создаёт новую пробную копию. После обновления административные команды выполняйте из текущего `WorkingDirectory` службы с окружением этой версии.
